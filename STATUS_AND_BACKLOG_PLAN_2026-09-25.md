### 2.2. Раунд 1 — `68ab2fc`, `b51bde8`

Схема «резерв -> генерация -> расчёт» в `src/api/services/billing.py`:
- `reserve_for_request` (строки 291-335) атомарно резервирует worst-case
  (prompt + max_tokens) до апстрима; `max_tokens` сужается под баланс, но не
  ниже `MIN_RESERVE_OUT_TOKENS = 256`; если не хватает даже на минимум —
  402 `insufficient_quota` с `required_kopecks`, `balance_kopecks`,
  `top_up_url`, и апстрим не вызывается вообще;
- `settle_reservation` (347-398): возврат неиспользованного, доплата
  перерасхода, fail-closed при отсутствии usage (расчёт по оценке, не по нулю);
- `release_reservation`, `flat_charge`, `flat_refund` — полный возврат и
  фиксированные списания;
- заголовки `X-Aineron-Balance-Kopecks`, `X-Aineron-Low-Balance`,
  `X-Aineron-Top-Up-Url`; сообщение 402 на .net — на английском (`b51bde8`,
  ветка по `INTL_MODE` в `_insufficient`).

Применено к: chat completions (stream и non-stream), `/messages`
(Anthropic), эмбеддинги (были бесплатны: в каталоге нет строк эмбеддингов ->
`network=None` -> списание пропускалось), batch, ASR/TTS, describe и
enhance-prompt, изображения (результат `spend_kopecks` не проверялся,

### 2.6. Уроки — правила для будущего кода

1. Никогда не вызывать `spend_kopecks` без проверки возвращаемого значения.
2. Платный эндпоинт резервирует или списывает **до** вызова апстрима;
   после — только расчёт/возврат.
3. Повторно использованный `reference` превращает `spend_kopecks` в тихий
   no-op, возвращающий `True` (`users/models.py:692-695`; уникальность
   `(type, reference)` глобальная, не на пользователя —
   `uniq_balance_txn_type_reference`). Для повторяемых действий — уникальный
   reference на попытку; для защиты от повторной доставки — явная проверка
   существования, как в `_charge_once`.
4. `type(request.user)` — это `SimpleLazyObject`, не модель; не строить на
   нём `objects.filter`.
5. `Decimal('NaN') <= 0` бросает исключение — валидировать `is_finite()` до
   сравнений.
6. Возврат делать на **фактически списанную** сумму (из леджера), а не на
   пересчитанную из настроек цену.

### 3.2. ITEM 2 — секретарь генерирует черновики до какого-либо списания

#### Как устроено сейчас (проверено)

`on_business_message` (`business.py:468-628`): гейты — `can_reply`, scope,
стоп-слово, дневной cap `_check_daily_cap` (Redis INCR, `BUSINESS_DAILY_REPLY_CAP=200`
на подключение, **fail-open** при сбое Redis — строка 323), `_has_enough_for_reply`
(`cb535e3`: баланс >= 1 ₽ или свободная квота), затем `generate_reply` —
вызов LLM и `hybrid_search` (эмбеддинги RAG, строка 90) на **каждое** сообщение
клиента. Списание (`_charge_reply`, 172-236) — только при «Отправить», при
отправке отредактированного текста или при уверенном автоответе. «Игнор»
(664-677) и истечение черновика не стоят владельцу ничего, а
`cleanup_business_drafts` (`telegram_bot/tasks.py:562-573`) через 7 дней
просто удаляет строки. Так как ничего не списывается, `_has_enough_for_reply`
остаётся истинным: владелец с 1 ₽ получает до 200 бесплатных генераций в
день. Вызов `cb_bizdraft_check` (чек-лист, 742-775) — ещё один LLM-вызов без
списания (дешёвая модель, 300 токенов). Кнопки «Перегенерировать» в коде нет;
«Изменить» — ручной текст владельца.

Статусы `BusinessDraft` (`telegram_bot/models.py:548-552`): pending, sent,
ignored, auto. `cb_bizdraft_ignore` помечает черновик безусловно
(`_mark_draft`, без проверки текущего статуса).

Экспозиция: `settings.py` (комментарий у `BUSINESS_AUTOPILOT_BURST_LIMIT`)
фиксирует «0 подключений в проде» — дата замера неизвестна. Проверить на
проде: `BusinessConnection.objects.filter(is_enabled=True, secretary_on=True).count()`.
Секретарь работает только на .ru (на .net роутер `business` не подключён).
Потеря на подключение в день при cap 200 (оценка): Sonnet 5 — до 192 ₽,
Opus — до 478 ₽, GPT-5.5 Pro — до 3184 ₽ (200 x потолок из таблицы 3.1);
после ITEM 1 (порог модели) — до ~192 ₽.

#### Варианты

| | Суть | Плюсы | Минусы |
|---|---|---|---|
| 2A. Списание за генерацию, без возврата за игнор | Цена ответа списывается до LLM; «Отправить» бесплатно | Закрывает утечку полностью; баланс-гейт снова работает | Владелец платит за черновики, которые не отправил; меняется смысл «1 ₽ за ответ» |
| 2B. Списание за генерацию, полный возврат за игнор/истечение | Как 2A + возврат | Для владельца как сейчас | Утечка остаётся: игнор = бесплатный черновик, текст можно скопировать вручную |
| 2C. Резерв + частичный возврат | Возврат доли (например, 50%) при игнор/истечении | Компромисс | Сложнее объяснить; утечка половинная |
| 2D. Лимит неразобранных черновиков | Не генерировать, пока pending >= N | Ограничивает поток | Сам по себе не делает генерацию платной |
| 2E. Квота по тарифу вместо денег | Считать генерации против 300/мес | Уже есть счётчик | Без тарифа проблема остаётся |

#### Рекомендация: 2A + 2D + квота считается по генерациям

Генерация — и есть оказанная услуга; возврат за игнор повторяет ту же
бесплатную петлю. Доля возврата — настройка `BUSINESS_UNUSED_DRAFT_REFUND_PCT`
(дефолт 0), чтобы владелец мог выбрать 2C без переписывания кода.

#### Машина состояний

```
(входящее) --гейты--> generating --LLM ok--> pending --Отправить/Изменить--> sent
                          |                    |--Игнор------------------> ignored   (возврат PCT)
                          |                    |--TTL-------------------> expired   (возврат PCT)
                          |--LLM ошибка / зависание > 15 мин--> failed        (полный возврат)
                          |--автопилот, уверен, доставлено--> auto
автопилот: неуверен / burst / доставка не удалась --> pending (без возврата)
sent --доставка не удалась--> pending (откат claim, без возврата и без нового списания)
```

Правила:
1. Черновик создаётся в статусе `generating` **до** списания; списание —
   `spend_kopecks(price, reference=f'bizgen:{draft.pk}')`; при отказе —
   строка удаляется, владелец получает сообщение клиента без черновика.
2. Квота «Бизнес»/«Макс» занимается при генерации тем же условным UPDATE,
   что в `_charge_reply` (строки 217-220); если занят бесплатный слот —
   списания нет (факт оплаты определяется наличием `spend bizgen:{pk}` в леджере).
3. Все переходы — условный `UPDATE ... WHERE status=<откуда>`; деньги
   двигаются, только если обновлена ровно одна строка.
4. Возврат — `add_kopecks(amount, type='refund', reference=f'bizgen:{pk}')`,
   где `amount` = фактически списанное (из леджера) x PCT. Если оплачено
   квотой — вместо денег `replies_this_month - 1` (только при полном возврате).
5. «Отправить», «Изменить», автоответ — без списаний; `charge_reply`
   и `refund_reply` в этих путях убираются; откат счётчика
   `_refund_reply:250-252` больше не нужен.
6. Повторная доставка апдейта Telegram: `cache.add(f'bizmsg:{conn.pk}:{chat_id}:{message.message_id}', 1, 86400)`
   до создания черновика; при сбое Redis — fail-open (дубль будет платным, не бесплатным).
7. Дневной cap при сбое Redis — фолбэк на счёт в БД
   (`BusinessDraft.objects.filter(connection=conn, created_at__date=today).count()`).
8. `BUSINESS_MAX_PENDING_DRAFTS` (предложение: 30): при превышении — не
   генерировать, переслать сообщение владельцу с пометкой.

Отказы и защита от них:
- Двойной возврат — невозможен: уникальность `(type='refund', reference)`
  и условный переход.
- Возврат после отправки — невозможен: возврат только из `pending`/`generating`,
  а отправка атомарно переводит `pending -> sent`. Сейчас «Игнор» после
  «Отправить» перезаписал бы `sent` на `ignored` — исправляется условным UPDATE.
- Сбой между списанием и LLM — черновик остаётся в `generating`; beat-задача
  через 15 минут переводит его в `failed` с полным возвратом.
- Редеплой бота во время генерации — тот же путь.

Celery/beat: новая задача `telegram_bot.tasks.expire_business_drafts`
(каждый час) — `pending` старше `BUSINESS_DRAFT_EXPIRE_HOURS` (предложение:
72) -> `expired` + возврат PCT; `generating` старше 15 минут -> `failed` +
полный возврат. `cleanup_business_drafts` (удаление через 7 дней) остаётся,
но не трогает `generating`. Регистрация — в `setup_periodic_tasks.py`.

Миграция: только `AlterField` choices у `BusinessDraft.status` (добавить
`generating`, `expired`, `failed`; `generating` — ровно 10 символов,
`max_length=10`). SQL не меняется, но файл миграции нужно закоммитить явно:
контейнер `web` выполняет `makemigrations` при старте (CLAUDE.md), и без
закоммиченного файла каждый инстанс сгенерирует свою миграцию — риск
расхождения `django_migrations`.

Тексты: карточка черновика — «Черновик готов · списано 1 ₽» (или «из
квоты»); `/secretary` — «Черновиков в этом месяце»; лендинг
`business-bot/page.tsx:101` и `TARIFFS.md` — «300 черновиков/ответов» —
согласовать с владельцем.

Тесты (`src/telegram_bot/tests_business_billing.py`): списание до LLM;
нет денег -> нет LLM (мок клиента не вызван); квота занимается при

«Отправить» — no-op; `expire_business_drafts` идемпотентна при двойном
запуске; зависший `generating` -> `failed` + возврат; повтор апдейта с тем же
`message_id` не создаёт второй черновик; сбой Redis -> cap по БД.

### 3.3. Прочие отложенные пункты

Серьёзность: высокая / средняя / низкая. Объём: S (до дня), M (2-4 дня), L (неделя+).
Пункты, помеченные «по данным аудита», мной не перепроверялись.

1. **Фарм стартового гранта сверх rate-limit** — средняя, M. Лимит
   `TG_SIGNUP_GRANTS_PER_HOUR/DAY` обрезает массовый фарм, но 200 грантов в
   сутки по 10 ₽ всё равно выдаются любым аккаунтам. Направление: грант
   только после `request_contact` (кнопка «Поделиться номером»), один грант
   на хэш телефона; additive-миграция (поле `phone_hash` с индексом, пустой
   дефолт).
2. **ASR в боте без лимита длительности, 1 ₽ после апстрима** — средняя, S.
   `voice.py:123` вызывает транскрипцию, списание — только на строке 133;
   длительность голосового не проверяется. Направление: `message.voice.duration`
   <= лимит, цена по минутам, `flat_charge` до вызова и возврат при ошибке.
3. **Повторная доставка Celery для медиа** — низкая, S. Reference
   `media:{message.id}` при редоставке даёт бесплатную вторую генерацию;
   `acks_late` в настройках не задан (grep пуст), поэтому редоставка
   маловероятна. Направление: проверять статус сообщения и наличие
   `_video_task`/результата до повторного вызова апстрима.
4. **Курс Telegram Stars** — средняя, бизнес-проверка. `payment.py:671,731`:
   `xtr = max(1, rub // 2)` — 1 XTR = 2 ₽ на баланс. Сверить с фактической
   выплатой Telegram за 1 XTR и комиссией вывода.
5. **Реферальный бонус** — средняя, M (по данным аудита): бонус не
   отзывается при возврате платежа, нет защиты от самореферала при веб-атрибуции
   `?ref=`. Направление: отзыв `referral` по reference платежа при refund;
   запрет, если реферер совпадает по IP/устройству/email-домену.
6. **Неучтённые мелкие вызовы и квота Tavily** — средняя, M. Извлечение
   памяти, резюме чатов, эмбеддинги базы знаний, опрос коннекторов, поиск на
   каждое сообщение с «Интернет». Бесплатный Tavily — 1000 запросов/мес;
   одно исследование — 5 (или больше, см. 3.1), агент — до 6. Направление:
   счётчик Tavily-вызовов в Redis с алертом на 80%; цена за поиск в чате.
7. **Детали overage** — средняя, S. `PREFLIGHT_MIN_MAX_TOKENS = 1024`
   (`aitext/token_metering.py:214,295`): пользователь с нулевым балансом всё
   равно получает >= 1024 выходных токенов; по данным аудита overage
   пропускается, если SSE обрывается до чанка с usage (осознанно, строка 633
   плана). Направление: клэмп до `MIN_RESERVE_OUT_TOKENS` и fail-closed
   оценка при обрыве.
8. **Цепочка видео-фолбэка** — средняя, M. `generate_with_falai`
   (`fal_utils.py:2968-3010`): apimart -> CometAPI -> laozhang, каждый шаг
   может выставить нам счёт при одном списании пользователя. Поллинг: apimart
   120 попыток (20 x 3 с + 100 x 8 с = ~14 мин), CometAPI 90 x 5 с = 7,5 мин,
   laozhang ~14 мин — вместе ~36 мин против `CELERY_TASK_TIME_LIMIT = 30 * 60`
   (`settings.py:347`); аудит оценивал ~45 мин. Направление: не переходить к
   следующему провайдеру после того, как задача принята предыдущим; общий
   дедлайн цепочки < time limit.
9. **Регенерация с устаревшим `reasoning_effort` без доплаты** — низкая, S
   (по данным аудита). Направление: пересчитывать доплату при регенерации.
10. **Авторетраи SDK** — средняя, S. Клиенты создаются без `max_retries`
    (`aitext/providers.py:199`), по умолчанию OpenAI SDK делает 2 повтора; при
    read timeout апстрим может выполнить запрос до 3 раз. Направление:
    `max_retries=0` для генеративных вызовов, ретраи — на нашем уровне с
    учётом идемпотентности.
11. **Фронт не показывает низкий баланс** — средняя, S. Заголовки
    `X-Aineron-*` и `top_up_url` из 402 используются только в api-docs
    (grep по `frontend/lib`, `components`, `app`). Направление: баннер в чате
    и ссылка пополнения на 402.
12. **Гигиена окружения** — средняя, S. `TEXT_BILLING_ENABLED=0` на проде
    (по `c0aea58`); в локальном `.env:12` комментарий «код её не читает» —

    В корне мусор: `NUL` (в корне, `src/`, `src/telegram_bot/`, `frontend/`,
    `frontend/app/[locale]/`), `faq_dump.json`, `home_dump.json`,

    Первую строку `TOKEN_OVERAGE_BILLING_PLAN.md` вернуть:
    `git checkout -- TOKEN_OVERAGE_BILLING_PLAN.md`.
13. **Ставка dev-API за токен** — высокая, если подтвердится, S на проверку.
    Это не утечка, а переплата клиентов API и лишние 402: `reserve_for_request`
    по той же ставке резервирует больше и раньше сужает ответ.

    дороже. Команды, заполняющей поле, в репозитории нет. Проверить значения на проде.

## 5. Приложение

Тесты биллинга локально (остальные наборы локально падают только из-за
отсутствия Redis):

```bash
cd src && SECRET_KEY=x ../venv/Scripts/python manage.py test api.tests_reserve_billing api.tests_audit_fixes
```

Серверы:
- aineron.ru: `ssh aineron-ru`, каталог `/root/ai`, команда `docker-compose`.
- aineron.net: `ssh aineron-net`, каталог `/opt/aineron`,
  `docker compose -f docker-compose.intl.yml`.

Деплой: после инкрементального
`up -d --no-deps web daphne celery_worker celery_beat` обязательно
`restart nginx`, иначе 502 (nginx держит старые IP апстримов).

Правило CLAUDE.md: любое различие поведения между инстансами — только через
`settings.INTL_MODE`, с безопасным дефолтом; data-миграции — instance-agnostic;
после изменения общего кода деплоить оба инстанса близко по времени.

Полезные факты:
- Уникальность леджера: `(type, reference)` глобально, при непустом reference.
- Префиксы reference: `agent:{run_id}`, `research:{message_id}`,
  `aitask:{task_id}:{run_iso}`, `bizreply:{draft_id}:{uuid12}`,
  `api:{request_id}`, `media:{message_id}`, `chat:{message_id}`;
  предлагается `bizgen:{draft_id}`.
- Мониторинг «списано без результата» — `reconcile_stuck_spends`
  (`aitext/tasks.py:2492`), покрывает `chat:`, `chat-regen:`, `compare:`,
  `media:`, `research:`; `agent:` и `bizreply:`/`bizgen:` не покрыты.
