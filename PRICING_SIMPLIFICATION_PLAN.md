# PRICING_SIMPLIFICATION_PLAN.md

Два связанных решения: (1) замена основного текстового/медиа провайдера
laozhang.ai (частые перегрузки, недоступность новых флагманов) на связку
OpenRouter (основной) + apimart.ai (резерв) + laozhang.ai или kie.ai
(третий, на крайний случай) — §1.1; (2) переход розничных цен на текстовые
модели на простую формулу «себестоимость провайдера × единая наценка», в
рублях за 1М токенов — как у RouterAI и большинства реселлеров, вместо
ручных плоских цен за сообщение, подобранных на глаз — §2-3. Сначала —
только `[.ru]`, каталог/цены/провайдер. Билинг-движок (списание за
сообщение) в этом плане **не меняется** — см. §4 почему.

Статус: **Фаза 1 (§7) в основном реализована 2026-09-02/03** — см. журнал
в §9. Фаза 0 (переезд провайдера на OpenRouter) **не начата** — текст и
изображения по-прежнему идут через laozhang.ai/apimart.ai, провайдерное
решение (§1.2) зафиксировано в плане, но код не менялся. Дата составления:
2026-09-02, дополнено 2026-09-02 (исследование провайдеров, §1.1), журнал
реализации добавлен 2026-09-03 (§9).

## 0. Вывод сразу

Цены не «занижены» произвольно — они **не привязаны к токенам вообще**.
Сейчас `NeuralNetwork.cost_kopecks` — плоская цена за сообщение (22 ₽ за
любое сообщение к Opus 5, короткое или на 15000 токенов контекста). При такой
модели лёгкие сообщения переплачивают, тяжёлые — сильно недоплачивают, и
именно тяжёлый хвост создаёт ощущение «мы теряем деньги». RouterAI и все
реселлеры в скриншотах продают **по факту потреблённых токенов**, поэтому их
цены выглядят «настоящими» — сравнение исходно было некорректным (сообщение
vs. токен).

Разумный первый шаг — не менять сам движок списания (он и так работает,
рискованно трогать SSE/Celery-путь ради этого), а:
1. Считать розничные ₽/1М токенов по единой простой формуле от опта — как
   RouterAI считает свои. Это даёт честную для сравнения таблицу.
2. Из этой ставки пересчитать плоские цены за сообщение (`cost_kopecks`) по
   типовому профилю токенов на класс модели — так же просто, без адаптивных
   пересчётов «по факту».
3. Каталог показывает и ₽/1М (как у конкурента), и итоговую плоскую цену за
   сообщение — прозрачно и сравнимо.

Настоящий переход на билинг по факту токенов (как у RouterAI) — отдельное,
более рискованное решение, вынесено в §7 как отдельная фаза, не в этом заходе.

## 1. Себестоимость: что у нас уже есть и чему можно верить

аудированная в рамках `TOKEN_OVERAGE_BILLING_PLAN.md` для 7 моделей. Для
Claude Opus 5: `(5.0, 25.0)` — **совпадает** с листовой ценой OpenRouter

провайдера, вопрос «чему верить как себестоимости» во многом снимается сам
собой — опт для OpenRouter это не оценка «сверху», а **точная цена, которую
мы реально будем платить** (см. таблицу в §1.1). Буфер ×0.8 из старой

только для моделей, для которых ещё нет точных цифр OpenRouter (см. §8.1).

### 1.2. Рекомендация

**Основной: OpenRouter.** Не самый дешёвый (цена = чистый лист, без чьей-либо
наценки — но это нормально, свою розничную наценку мы всё равно накидываем
поверх любого опта, см. §2), зато единственный, где надёжность решена
архитектурно (автофейловер между независимыми провайдерами одной модели), а
не обещанием SLA. Именно это и есть лекарство от проблемы «laozhang часто
недоступен / новых моделей нет» — а не просто более дешёвый counterpart той
же однобэкендной схемы. Интеграция — минимальная (тот же паттерн, что и
сейчас с laozhang). Оплата из РФ подтверждена вживую через крипту.

**Резервный: apimart.ai.** Дешевле (в среднем на ~20% ниже листа), уже
интегрирован у нас для видео тем же кодом, тот же тип API (без адаптеров).
Хорошо подходит как второй канал в `FallbackClient` (уже есть паттерн
laozhang↔apimart — переиспользовать на openrouter↔apimart). Оплату из РФ
пользователь проверяет самостоятельно (снято с плана как открытый пункт).

**Третий, «на крайний случай»: laozhang.ai — решено.** Код уже написан и
работает большую часть времени (проблема — в пиках, не в 100% отказе), ноль
доп. интеграции. kie.ai рассмотрен и отклонён — риск повторить именно ту
проблему, из-за которой уходим с laozhang (зависшие генерации со списанием,
недоступный Sora несмотря на прайс, прецедент тихого удаления модели), плюс
отдельная разработка под неоднородный API.

## 2. Формула наценки — максимально простая, без ручной подгонки

Реверс-инжиниринг RouterAI по их же каталогу (`Screenshot_64/65/68/69.png`):

| Модель | Их цена ₽/1M IN | Опт OpenRouter $/1M IN | Подразумеваемый курс |
|---|---|---|---|
| Claude Sonnet 5 | 222 ₽ | $2 | 111.0 |
| Claude Opus 5 | 561 ₽ | $5 | 112.2 |
| Claude Fable 5.1 | 1122 ₽ | $10 | 112.2 |

Совпадает на выходных токенах теми же коэффициентами (2807/25=112.28,
1112/10=111.2, 5614/50=112.28). **Вывод: у RouterAI нет наценки по модели
вообще — они просто продают лист-цену OpenRouter по фиксированному курсу
~112 ₽/$, и весь их «маржин» — это разница между 112 и спотовым курсом.**
Ровно то простое устройство, которое просит пользователь.

### 2.1. Предлагаемая формула

```
цена_₽_за_1М(direction) = опт_$_за_1М(direction) × K
```

Один глобальный константный коэффициент `K` (₽ за $ опта), без исключений
по модели — как у RouterAI. Никакой адаптивной подстройки по факту токенов,
порогов, капов (это как раз то усложнение, которое уже есть в
`TOKEN_OVERAGE_BILLING_PLAN.md` — `TOKEN_OVERAGE_MARKUP` × `TOKEN_OVERAGE_MIN_FRACTION` ×
`TOKEN_OVERAGE_CAP_MULTIPLE` — и от которого пользователь просит уйти для
основной цены; overage остаётся отдельным, уже задеплоенным страховочным
механизмом на 5 тяжёлых моделей, см. §4).

**Как выбрать K — пересчитано на реальном споте (2026-09-02, был вопрос
пользователя «какая тогда будет маржа»):**

Курс ЦБ на 2 сентября 2026 — **86,75 ₽/$** ([finance.mail.ru](https://finance.mail.ru/currency/cbrf/usd/),
[ЦБ РФ](https://www.vedomosti.ru/finance/news/2026/09/01/1225424-povisil-kursi)) — заметно выше, чем
`TOKEN_OVERAGE_USD_RUB=80` в `settings.py:664` (устарело, датировано
2026-08-05, **не использовать без обновления**). Плюс — OpenRouter берёт
**5% комиссию на топап** (крипта USDC, §1.1) — это реальная надбавка к
себестоимости закупки, не только к цене продажи. Итоговая цена закупки
1$ опта для нас: `86.75 × 1.05 ≈ 91.1 ₽`.

Опт `опт_$` после переезда на OpenRouter (§1.1) — это уже не оценка, а
фактическая цена закупки, без буфера ×0.8 (тот буфер был калибровкой под
laozhang, к OpenRouter-листу неприменим). Маржа = `K / 91.1`:

| K | Позиция к RouterAI (112.2) | Маржа над фактической закупкой (OpenRouter + fee) |
|---|---|---|
| 112 | паритет с RouterAI | ×1.23 (~23%) |
| 105 | дешевле на ~6% | ×1.15 (~15%) |
| 100 | дешевле на ~11% | ×1.10 (~10%) |
| 95 | дешевле на ~15% | ×1.04 (~4%) |

**Прямой ответ на вопрос «смогу ли конкурировать с RouterAI и какая будет
маржа»:** да, паритет по цене (K≈112) достижим и даёт ~23% валовой маржи —
до вычета своих же издержек (Robokassa/эквайринг на пополнение баланса
пользователем — обычно 3-5%, минимальные списания по `MIN_CHARGE_KOPECKS`
на дешёвых моделях, бесплатные/безлимитные сообщения по тарифам). После
этого чистая маржа реалистично ~15-18%, а не 23%. **Демпинговать ниже
паритета (K<112) уже рискованно** — на K=100 (−11% к RouterAI) валовая
маржа падает до ~10%, чистая может уйти в околонулевую или отрицательную
зону на части трафика. Дополнительная оговорка: у RouterAI, скорее всего,
опт **дешевле нашего** — крупный реселлер обычно закупает у провайдеров
напрямую по wholesale, не по публичному листу OpenRouter (ровно так же, как
apimart/kie.ai продают на 20-60% ниже листа и остаются прибыльными, см.
§1.1) — то есть их реальная маржа при той же розничной цене, вероятно,
выше нашей. Мы физически не можем узнать их опт, только предполагать по
аналогии с apimart/kie.ai.

**Рекомендация с учётом пересчёта:** K=105-112 (не ниже) как старт, с
явным пониманием, что это работает на паритете/лёгком дисконте, не на
агрессивном демпинге. Если нужна более здоровая маржа без потери
конкурентности по цене — рассмотреть вариант (в): для моделей, где через
резервный apimart закупка стабильно дешевле листа (подтверждено для Claude
семейства — на 20%, но не универсально, для gpt-5.6-sol наоборот
OpenRouter дешевле апимарта, см. §5) — считать себестоимость от более
дешёвого источника трафика, а не от OpenRouter по умолчанию. Это требует
знать фактическое распределение трафика primary/fallback по каждой
модели — не оценивается заранее, а меряется после переезда (Фаза 0, §7).
Финальное K и подтверждение экономики — открытый пункт §8.2.

### 2.2. Единицы для не-текстовых моделей — не втискивать в токены

Пользователь сравнивал в основном текстовые модели, но каталог шире:
- **Текст** — ₽/1М input, ₽/1М output (эта формула).
- **Изображения** — ₽ за генерацию (как сейчас, `cost_kopecks` за сообщение
  уже корректная единица — не трогать).
- **Видео** — ₽ за секунду (RouterAI показывает именно так: «Секунда
  видео: 15 ₽» на скриншоте Wan 3.0). Апдейт по apimart-исследованию: у
  apimart Sora 2 и Kling v2.6 (наша текущая модель) уже посекундные тарифы
  ($0.08/сек и $0.037-0.15/сек соответственно), а Veo3.1 — за вызов, не за
  секунду (`$0.14-1/вызов`) — то есть единица тарификации у провайдера
  **разная по моделям**, наше решение «₽/сек для всех» не всегда 1:1
  ложится на опт. Также apimart предупреждает: параметры Sora 2 изменились
  (duration теперь 4/8/12/16/20 сек, не 5/10/20 как записано в CLAUDE.md) —
  перепроверить при следующем контакте с video-API независимо от выбора
  провайдера. Возможно, отдельный follow-up, не в этом плане.

## 3. Что из плоской цены за сообщение получается

Плоская цена за сообщение остаётся (движок списания не меняем), но теперь
**выводится** из ₽/1М по типовому профилю токенов на класс модели, а не
подбирается на глаз. Три профиля (грубая, но простая и фиксированная
оценка — не пересчитывается по факту):

| Профиль | Типичный input (с историей) | Типичный output | Модели |
|---|---|---|---|
| short | 3000 ток. | 800 ток. | GLM Flash, Qwen Flash, GPT-4o-mini класс |
| standard | 6000 ток. | 1500 ток. | GPT-5, Sonnet, Gemini Pro класс |
| heavy/thinking | 10000 ток. | 4000 ток. | Opus, Fable, GPT-5-pro, thinking-варианты |

```
cost_kopecks = round(
    (input_tokens × price_in_rub_per_1m + output_tokens × price_out_rub_per_1m) / 1_000_000 × 100
)
```

Пример на K=105, профиль heavy, Opus 5 (опт $5/$25 → 525₽/2625₽ за 1М):
`(10000×525 + 4000×2625) / 1 000 000` = `(5 250 000 + 10 500 000) / 1 000 000`
= `15.75 ₽` → `cost_kopecks = 1575` (15,75 ₽). **Ниже текущих 22 ₽** — то есть
типичное «тяжёлое» сообщение сегодня и так не убыточно по этой оценке,
проблема именно в хвосте (контекст на 20 сообщений, thinking, output у
потолка 16384 токенов — там реальная себестоимость легко уходит за 60-80 ₽,
см. `TOKEN_OVERAGE_BILLING_PLAN.md:931` реальный кейс gpt-5.4-pro на ~13000
ток. вышел на ~187 ₽ по формуле). Плоская цена не обязана расти на всех
моделях — там, где текущая цена уже выше расчётной, её трогать не нужно (не
понижать искусственно прибыльные модели ради формулы).

**Тяжёлый хвост (реальный контекст 15-20 сообщений + thinking + большой
output) остаётся недо-покрыт флэт-ценой в принципе** — для этого уже
существует и частично задеплоен overage (`TOKEN_OVERAGE_BILLING_PLAN.md`,

см. §4). Этот план его не заменяет, а делает саму базовую (плоскую) цену

## 7. Фазы

**Провайдерное решение зафиксировано (2026-09-02):** основной — OpenRouter,
резервный — apimart.ai (оплату проверяет пользователь самостоятельно),
третий/крайний случай — laozhang.ai (остаётся как есть, без доп. работы).

1. Оплата: OpenRouter — крипта USDC подтверждена вживую (§1.1); apimart —
   проверяет пользователь сам, вне этого плана.
2. Сгенерировать API-ключи, добавить `OPENROUTER_API_KEY` рядом с
   существующими `LAOZHANG_API_KEY`/`APIMART_API_KEY` в `.env`.
3. В коде, где сейчас `base_url` указывает на laozhang (текстовые/картиночные

   (уже есть как fallback, тип API не меняется), laozhang — третьим/крайним.
4. Живой прогон на нескольких моделях (включая Opus 5, чтобы проверить
   именно ту проблему, из-за которой уходим с laozhang) на обоих

5. `model_name` в `NeuralNetwork` для многих моделей может не совпадать

   смаппить перед переключением, иначе часть моделей молча перестанет
   работать.

**Фаза 1 («сначала добавим модели», после Фазы 0 или параллельно с ней —
выбор провайдера и пересчёт цен независимы друг от друга):**
1. Зафиксировать K (открытый пункт §8.2) и профили токенов (§3).
2. Добавить `price_in_kopecks_per_1m` / `price_out_kopecks_per_1m` в
   `NeuralNetwork` — additive-миграция, safe default `NULL`/0 (см. CLAUDE.md
   правило 3), используется только для отображения и для расчёта дефолтной
   `cost_kopecks` при создании/обновлении через management-команду — не
   мигрирует автоматически существующие вручную выставленные цены.
3. Обновить `add_laozhang_models.py`: для новых записей — цена из формулы,
   не с потолка. Для уже существующих моделей **не откатывать** вручную
   скорректированные цены молча (в `TOKEN_OVERAGE_BILLING_PLAN.md:827` уже
   зафиксирована эта ловушка — команда переписывала цену на устаревшую).
4. Добавить content-содержательные пробелы из §6 (GLM дешёвый тир, Qwen
   vision, Grok reasoning-варианты — приоритет, остальное по вкусу).
5. Фронтенд `/models/`: карточка вида RouterAI (`Screenshot_64.png`) —
   «Входящие токены за 1М: N ₽», «Исходящие токены за 1М: M ₽» — рядом с
   текущей ценой за сообщение, не вместо неё.

**Фаза 2 (отдельное решение, не старт по умолчанию):** реальный билинг по
факту токенов (замена/расширение flat) — это по сути включение уже
существующего `token_metering.py` + `TOKEN_OVERAGE_ENABLED=1` не только как
overage, а как основной механизм. Требует отдельного решения — это ровно та
«сложная пересчётная» машина, от которой пользователь просил уйти для
базовой цены; обсуждать отдельно, если после Фазы 1 разница между плоской
и реальной ценой останется ощутимой на практике.

4 модели заведены как новые записи `NeuralNetwork`, которых раньше не было

### 9.3. Реальный биллинг (`cost_kopecks`) переписан — не только каталог

§4 говорил «движок списания не трогаем» — в итоге сам движок (`spend_kopecks`)
не менялся, но **значения `cost_kopecks` в БД переписаны напрямую**, а не
оставлены как «параллельная витринная цифра» (как предполагалось в §1
«показывать оба числа, реальную не трогать»). Пользователь явно потребовал
именно перезаписать реальный биллинг под новую формулу.

- **Текст**: `standard`-профиль (6000 вход / 1500 выход, §3) применён
  единообразно ко всем 21 текстовым моделям, не `short`/`heavy` по классу
  модели, как предполагал черновик §3.
- **Картинки**: `cost_kopecks = round(priceGenRub × 100)` напрямую, без
  профиля.
- **Видео**: `cost_kopecks = round(priceVideoRub × реальная_длительность_по_умолчанию × 100)`,
  где длительность взята из `config_json.api_defaults.duration` (реальная,
  не предположение) — закрывает открытый пункт §8.4 конкретной формулой.
- **Правило защиты от повышения** (первый проход, 2026-09-03): `новая_цена
  = min(старая_цена, расчётная_цена)` — цена никогда не растёт относительно
  того, что было. Бэкап цен до пересчёта: `/tmp/reprice_rollback_2026-09-03.json`
  на сервере aineron.ru.
- **Видео — второй проход, поднятие цены до уровня конкурента** (2026-09-03,
  по прямому запросу пользователя, отменяет правило "не повышать" выше для
  видео): 16 из 24 видео-моделей, где есть точное соответствие у RouterAI
  (сверено живьём на routerai.ru/ai-video), цена **поднята** до
  `(RouterAI_₽/сек × 0.95) × наша_реальная_длительность_по_умолчанию` —
  то есть ровно на 5% дешевле конкурента, а не занижена относительно
  расчёта. Пример: Sora 2 Pro 30₽→125.40₽, Veo 3.1 95₽→167.20₽. Оставшиеся
  8 видео-моделей (базовая Sora 2, Vidu, Pixverse, Kling Motion Control/3.0
  Turbo и т.д.) у RouterAI не продаются — не тронуты. Картинки под такой же
  проход (конкурент минус 5%) — в процессе на момент этой записи.

живо пересчитывается при смене любой настройки (`frontend/lib/utils/
mediaCost.ts`, зеркалит `validate_and_merge_settings` из `fal_utils.py`
1:1). На `/models/[slug]` добавлена таблица «Цена по настройкам»
(`components/models/ModelPriceTiers.tsx`) — строится из реального
`config_json`, не из статичных данных.

**Ограничение 4K+звук у Kling** (v3/v3 Omni/v3 Motion Control): CometAPI
явно пишет, что 4K доступен только без звука. Добавлен универсальный
механизм `config_json.constraints.incompatible` (проверяется в
`validate_and_merge_settings`, единая точка для веба и бота) + на фронте
конфликтующая настройка блокируется/автосбрасывается.

**Не выполнено (открыто, зафиксировано по прямому запросу пользователя —
не делать сейчас, но не терять из виду):**
- **П.3 — референс-видео как вход у Kling v3-omni/o1.** CometAPI отдельно
  тарифицирует режим «видео на входе» (0.1008–0.1344 $/сек, дороже обычного
  photo-референса) — у нас в UI нет такой настройки вообще (используем
  только `image_urls`, не видео-файл как референс). Чтобы добавить, нужна
  новая настройка/режим на фронте + поддержка в `generate_video_apimart()`.
- **П.4 — доплата за количество референс-фото у Grok Imagine 1.5.**
  CometAPI берёт $0.008 за каждое референс-изображение отдельно от цены
  вывода; у модели `i2v_max_images: 7` — пользователь может прикрепить
  до 7 фото бесплатно для нас. Текущий механизм `extra_cost` умеет считать
  доплату только за выбранное значение select/checkbox-поля, а не за
  «сколько файлов реально прикреплено» — нужен отдельный тип биллинга
  (доплата за количество вложений), которого сейчас нет ни у одной
  медиа-модели в каталоге.

### 9.8. Анализ Apimart vs CometAPI (Opus 5) + перекалибровка по реальному Apimart (2026-09-05)

Отдельный агент на Opus 5 сравнил реестр CometAPI с новым выверенным
реестром Apimart (`fb7b9382`) по всем видео-моделям и дал развёрнутый ответ
на архитектурный вопрос «делать ли два провайдера видео». Итог:

- **Второй провайдер (CometAPI) нужен НЕ ради цены** — на пересечении
  моделей разница обычно 5-16%, слишком мала для маршрутизации по цене
  (риски: разные бэкенды под одним именем у агрегаторов, двойное списание
  при неудачном фолбэке, обе цены сами по себе внутренне противоречивы на
  разных страницах своих сайтов). Настоящая причина — у нас сейчас **нет
  рабочего резерва**: `laozhang_fallback_model` прописан только у 2 моделей
  из 22, и Laozhang отдаёт 503 почти по всем видео.
- **Не маршрутизировать по цене** «дешевле = основной» — неверная логика
  (5 причин в отчёте: разрыв мал, разные бэкенды за одним именем,
  латентность фолбэка складывается, риск двойного списания, обе цены
  недостоверны).
- **Уникальные модели каждого провайдера — не добавлять автоматически.**
  7 из 14 уникальных позиций CometAPI — это весь Runway (video→video), для
  которого у нас нет UX «загрузить видео как референс» вообще. Реально
  ложится в наш контракт только Veo 3 / Veo 3 Fast (обычный t2v/i2v).
- **Технически:** нужна не плоская `video_api_fallback`, а список
  `metadata.video_fallbacks` (провайдер+модель+маппинг имён параметров),
  плюс провайдер должен персиститься вместе с `task_id` (иначе рестарт
  воркера при двух провайдерах = потерянное видео и двойное списание).
  Объём работы честно оценён как отдельный спринт (1-2 недели, зависит от
  того, единый ли у CometAPI эндпоинт видео или по-семейный) — **не начат**.
- **Порядок приоритетов от Opus**: сначала перекалибровка цен по реальному
  Apimart (деньги текут прямо сейчас), затем разведочный вызов CometAPI,
  затем персистенс провайдера, затем фолбэк-цепочка, затем добавление
  Veo 3/Veo 3 Fast в каталог. Интеграция CometAPI как провайдера —
  **отдельная задача, не начата**.

**Перекалибровка по реальному Apimart — сделана в этом же заходе.** Анализ
Opus нашёл, что предыдущий пересчёт (§9.7, через CometAPI-прокси) был
неточен в диапазоне от −88% до +800% по разным моделям — часть моделей
продавалась ниже опта. `update_video_pricing.py` переписан на реальные
числа реестра Apimart (`fb7b9382`) для 20 из 22 моделей (не тронуты:
`vidu-q3` — apimart дал только тир 1080p, не совпадающий с нашим базовым
540p). Попутно раскрыты два самостоятельных открытия, не следовавших из
отчёта Opus:
- **Veo 3.1 (все три SKU) тарифицируется Apimart ФИКСИРОВАННО ЗА ВЫЗОВ**,
  не за секунду — подтверждено живым запросом `GET /v1/models` на проде:
  наши `model_name` (`veo3.1-quality`, `veo3.1-fast`, `veo3.1-lite`, без
  суффиксов) существуют в реальном каталоге как отдельные ID канала
  «-ext», отличные от суффиксных `-official` (тарифицируемых за секунду).
  Прошлый пересчёт считал их за секунду — это была ошибка базиса, не
  только цифр (цена veo-3-1 упала с 268.80₽ до 105₽ за сообщение).
- **`grok-imagine-1-5` был сломан**: `model_name` в БД
  (`grok-imagine-1.5-video-ext`) не существует в реальном каталоге Apimart
  вообще (проверено тем же `GET /v1/models`) — 3 из 4 последних генераций
  падали (деньги возвращались корректно, фича просто не работала).
  Исправлено на `grok-imagine-1.5-video-apimart` (подтверждённый реальный
  ID) той же командой.

Метод верификации моделей (`GET https://api.apimart.ai/v1/models`, реальный
живой каталог из 295 моделей) стоит использовать и для будущих проверок
`model_name` перед доверием любым внешним прайс-реестрам — он самый
надёжный источник истины по фактически существующим ID.

### 9.9. Сверка Apimart vs CometAPI с конкурентом + CometAPI как реальный провайдер (2026-09-05)

**Сверка с конкурентом (Gen-API/RouterAI)**, 22 модели: там, где есть данные
обоих провайдеров (14 моделей), Apimart дешевле в 7, CometAPI — в 3
(Seedance 1.5 Pro/2.0 на 6-14% дешевле, **Vidu Q3 Turbo — почти вдвое
дешевле**, K=231 вместо 105), паритет — в 4 (все Kling кроме Motion Control
на std-тире, Vidu Q3 база). Прямо опровергнута гипотеза «CometAPI дешевле
и тарификация по секундам у Veo — это плюс»: на 8-секундном ролике
CometAPI-Veo (посекундно) выходит в 2.6-4.6 раза ДОРОЖЕ, чем Apimart
(плоско за вызов) — секундная тарификация здесь не выгоднее, а дороже.
Полная таблица с коэффициентом K к каждому провайдеру по каждой модели —
артефакт `199f0d7f`.

**Резервная ёмкость (K к CometAPI при текущей розничной цене)**: хороший
резерв (K≥90) — 9 моделей (Kling кроме Motion Control, весь Seedance кроме
Fast, оба Vidu Q3); тонкий (K 60-90) — Wan 2.6/2.7; рискованный (K<50) —
Veo 3.1×2, Grok Imagine 1.5 (маржа почти обнулится при реальном
переключении); резерва нет вообще — 8 моделей (Kling v2.6/3.0 Turbo/Motion
Control, оба Hailuo, Pixverse V6, Vidu Q3 Pro, Veo 3.1 Lite).

**CometAPI подключён как реальный провайдер — Veo 3 и Veo 3 Fast.**
Единственные модели, которых у Apimart нет вообще (только 3.1). Контракт
CometAPI для видео — `POST /v1/videos` (multipart form: model/prompt/
seconds/size) → `{id, status}`, поллинг `GET /v1/videos/{id}` →
`video_url` при `completed` — подтверждён живым тестовым вызовом ДО
написания кода, затем повторно проверен через реальный Celery-пайплайн
(`generate_ai_response` → списание 67.20₽ → генерация → сохранение файла,
всё сквозным тестом на проде, не только сырой API-вызов). Реализация:
`generate_video_cometapi()` в `fal_utils.py` (зеркалит структуру
`generate_video_apimart()` — тот же паттерн placeholder/resume-after-
restart/billing, свой ключ `_cometapi_task_id` в `message.content`, чтобы
не путать с apimart-задачами), роутинг по `metadata.video_api == 'cometapi'`,
ключ `COMETAPI_API_KEY` в `.env` (не в git). Цены: Veo 3 = 268.80₽,
Veo 3 Fast = 67.20₽ (K=105 от опта CometAPI, 4K = +134₽ у обеих).

**Ограничение MVP**: только text-to-video. CometAPI ждёт `input_reference`
как file (multipart), а не URL, как apimart везде — image-to-video
потребует скачать референс-фото и переотправить как файл, отдельная
доработка, `supports_image_to_video: False` в metadata обеих моделей пока
не сделано.

**Не сделано из плана §9.8** (осознанно, вне скоупа этого захода):
персистенс провайдера в `_video_task`/generic-фолбэк-цепочка через
`video_fallbacks` — CometAPI подключён как ПРЯМОЙ провайдер для двух
конкретных моделей, не как fallback для существующих apimart-моделей.
Если понадобится сделать резерв для моделей из «хорошая ёмкость» выше —
нужна отдельная реализация роутинга/фолбэка, код для этого не переиспользуется
автоматически из `generate_video_cometapi()` один-в-один (параметры/имена
полей у части моделей отличаются от apimart).
