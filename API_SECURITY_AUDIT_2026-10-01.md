# Аудит api/ — безопасность, корректность, документация (2026-10-01)

Многоагентное ревью (6 параллельных агентов на Opus) всего `src/api/` + публичной
документации (`frontend/app/api-docs/`) + смежных файлов (`users/views.py`,
инфраструктура). Два самых критичных пункта (№1, №2) лично перепроверены —
живым внешним тестом и прямым чтением кода, не только со слов агентов. Остальное —
находки агентов с точными `файл:строка`, не все перепроверены вручную (см. пометки).

Деньги не трогались, прод не менялся — это только фиксация находок.

## CRITICAL — требуют немедленного внимания

### 1. [ПОДТВЕРЖДЕНО ЖИВЬЁМ] Redis/Postgres/Django/Next.js открыты в интернет на aineron.ru, фаервола нет

- `docker-compose.yml` (.ru): `ports: "6379:6379"` (redis), `"5432:5432"` (postgres),
  `"8000:8000"` (gunicorn напрямую), `"3000:3000"` (Next.js напрямую).
- На сервере: `ufw status` → **inactive**, `iptables -L DOCKER-USER` → пусто,
  `iptables -L INPUT` → policy ACCEPT (только fail2ban на 22/ssh).
- **Живой тест с внешней машины на 155.212.131.87**: порты 6379, 5432, 8000, 3000 —
  **OPEN** (порт 8001 preview-service закрыт, т.к. сервис не поднят — profile studio).
- Redis — **без пароля** (`redis-server --appendonly yes`, нет `--requirepass`):
  любой из интернета может `redis-cli -h 155.212.131.87`, читать/писать/`FLUSHALL`
  брокер Celery, идемпотентные кэши, дневные капы, FSM Telegram-бота, счётчики
  rate-limit — и, в зависимости от конфигурации Celery, потенциально инжектить
  задачи.
- Postgres — пароль в `.env` **`neiro_pass_123`** (слабый, не ротировался). Порт
  открыт в интернет → полный доступ ко всей прод-базе (балансы, хэши API-ключей,
  персональные данные) без какой-либо дополнительной эксплуатации.
- `.net` (`docker-compose.intl.yml`) — только 80/443 наружу, там всё в порядке.

**Это не теоретический риск — порты реально открыты прямо сейчас.** Минимальный
безопасный фикс не требует пересборки: добавить к каждому `ports:` префикс
`127.0.0.1:` (например `"127.0.0.1:6379:6379"`) и пересоздать контейнеры, либо
поднять `ufw`/правила в `DOCKER-USER`, разрешив только 22/80/443 снаружи.
Межконтейнерная сеть (nginx→web, web→redis/db) работает через internal docker-сеть
по именам сервисов и это не трогает.

### 2. [ПОДТВЕРЖДЕНО ЧТЕНИЕМ КОДА] Захват чужого аккаунта перебором кода подтверждения email — анонимно, без rate-limit

- `GET /users/api/verify-email/<code>/` (`users/views.py:330` `verify_email()`,
  без `@login_required`) → `verify_email_token()` (`users/email_service.py:338-347`)
  при промахе по длинному токену **падает на поиск по 6-значному коду**:
  `CustomUser.objects.get(email_verification_code=token)`. При совпадении —
  `login(request, user, ...)` без проверки, кто спрашивал.
- Нигде по цепочке (`users/urls_api.py`, Django view, nginx.conf) **нет rate-limit**
  — ни `django-ratelimit`, ни DRF throttle (это legacy Django view, не DRF), ни
  `limit_req` в nginx (проверено — зоны лимитов в nginx.conf отсутствуют вовсе).
- Пространство кода — `10^6`, генерируется `random` (не `secrets`), без TTL.
  При ~100 неподтверждённых аккаунтов (оценка из памяти проекта) один хит —
  это порядка 10^4 анонимных GET-запросов без каких-либо ограничений.
  При попадании — чужая сессия, чужие чаты/файлы/баланс, и можно сразу выпускать
  API-ключи (email стал "подтверждён").
- POST-вариант (`/users/api/ajax/verify-email/`, `ajax_verify_email_code`,
  `users/views.py:348`) — та же уязвимость, но требует `@login_required` (чуть уже).
- Соседний баг той же природы: `POST /users/api/ajax/password-reset/`
  (`users/views.py:251`) меняет пароль **сразу**, без подтверждения по ссылке,
  шлёт новый пароль в письме открытым текстом, без rate-limit — позволяет
  анонимно и многократно "взрывать" пароль любого юзера по email (DoS аккаунта).
- На `.net` риск ниже: `email_verified=True` ставится сразу при `INTL_MODE`, код
  вообще не выдаётся.

**Фикс** (минимально инвазивный, не трогает фронт): искать код **в паре с текущим
залогиненным/сессионным пользователем**, а не по всей таблице; TTL + счётчик
попыток с блокировкой; генерировать код через `secrets`; добавить rate-limit
(хотя бы `django-ratelimit` по IP+email) на оба эндпоинта верификации и на
password-reset; убрать code-fallback из GET-пути вообще (ссылка должна пускать
только по длинному токену).

## MEDIUM

15. Токенная цена `/v1/chat/completions` при токенном биллинге (`kopecks_per_1k_tokens`
    не выставлен ни одной management-командой) выходит на **~15-кратную переплату**
    клиента против веба для одинакового объёма — не утечка денег площадки, а
    некорректный прайс для внешних разработчиков. `api/services/billing.py:19-25`.
16. `n>1` в chat/completions — резервируется и оплачивается `n` вариантов,
    возвращается только `choices[0]` (`chat.py:49,98,256`).
17. API-резервы (`api:{request_id}`) не покрыты `reconcile_stuck_spends` — падение
    воркера посреди запроса замораживает деньги пользователя навсегда,
    восстановления нет (`aitext/tasks.py:2588` не знает префикс `api:`).
18. Вывод реферальных денег без CSRF-защиты (`CsrfExemptSessionAuthentication`,
    `api/views/referral.py:79`) — реквизиты выплаты задаёт тело запроса, при
    любом same-site XSS/контенте весь `rub_balance` можно увести CSRF-POST'ом.
19. Анонимный сброс пароля позволяет перебирать существующие email (разный ответ
    "не найден" / успех) — `users/views.py:251`, см. также п.2.
20. `RegisterView` (DRF, `api/views/auth.py`) не ставит shadow-ban по IP — эта
    защита есть только в legacy `users/views.py`, а реальный фронт зовёт именно
    DRF-путь. На `.net` (email подтверждается сразу) это снимает защиту от фарма
    бесплатного гранта полностью.
21. JWT (Telegram Mini App) обходит shadow-ban — `ShadowBanMiddleware` видит
    только сессионных пользователей, `simplejwt` проверяет только `is_active`.
22. Ссылка привязки Telegram-бота молча перепривязывает уже существующий
    `TelegramUser` жертвы к новому аккаунту без подтверждения — угон истории
    чатов/Stars-платежей.
23. Один `exec {"background": true}` в Sandbox API обходит anti-abuse детектор
    (порог 50 exec) — майнер/прокси работает весь TTL незамеченным; egress VM
    ничем не ограничен (риск бана E2B-аккаунта платформы).
24. Sandbox: один дешёвый ключ может держать 30 параллельных `exec` с `sleep 300`
    на gunicorn (3×12=36 потоков) — укладывает весь `/api/` для всех пользователей
    (DoS через легитимный, оплаченный вызов).
25. AI-задачи по расписанию (`api/views/tasks.py`) — `network` произвольный FK,
    `prompt` без ограничения длины, биллинг плоский без overage-доплаты (в отличие
    от чата) — дорогая модель + гигантский промт по фиксированной цене до
    `AITASK_DAILY_CAP` раз в день.
26. `MemoryDetailView` — создатель орг-факта сохраняет право править его контент
    даже после выхода из организации (фильтр только `user=request.user`, не
    членство).
27. Зависшие Sandbox-сессии в статусе `STARTING` (нет `expires_at` до успешного
    create) — резерв и слот квоты занимают навсегда при любой ошибке, кроме
    `PreviewServiceError`.
28. Промокод начисляется (`add_kopecks`) **вне** транзакции, которая уже
    зафиксировала использование кода (`users/promo.py:166`) — сбой между шагами
    даёт "код сгорел, денег нет", без возможности повтора.
29. Пустой `TELEGRAM_BOT_TOKEN` (дефолт `''` в settings.py) делает HMAC-секрет
    initData предсказуемым (`HMAC("WebAppData", "")`) — актуально для
    staging/нового инстанса без токена, не для текущих .ru/.net (там токен задан).

## Документация `/api-docs/` — отдельный разрез (не безопасность, а "работает ли по инструкции")

Полный разбор — см. отчёт агента (doc-parity) в истории диалога. Коротко:
примеры для Anthropic SDK, TTS (`tts-1`), "видео через images/generations" и
"баланс через `/usage/`" в документации **не работают** при буквальном
копировании. Управление ключами (`scopes`, лимит 10, формат ответа) и полный
контракт вебхуков (подпись, события, которые реально отправляются) не описаны
вовсе. Три несогласованных источника "официального" контракта: кастомная
`/api-docs/`, автогенерируемый Swagger (`/v1/docs/`, видит вообще все эндпоинты)
и устаревший Postman.

## Рекомендованный порядок устранения

1. **Firewall на .ru** (№1) — минут на 10, полностью убирает самый серьёзный риск.
2. **Email-верификация + password-reset** (№2) — переписать поиск кода на
   привязку к сессии, добавить TTL/rate-limit.
3. Уточнить Trybit test_mode (№12) — если подтвердится CRITICAL, фикс простой
   (проверка флага).
4. SSRF вебхуков (№3), path traversal коннектора (№9), XSS через uploads (№10),
   эскалация через `/keys/` (№14) — все четыре закрываются точечно, без
   архитектурных изменений.
5. Остальной HIGH/MEDIUM — по мере сил, ни один не требует немедленной реакции
   при условии, что п.1–4 закрыты.
